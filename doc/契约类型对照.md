# 契约类型对照

前端标准化第 6 条要求「请求 / 响应类型由后端 `openapi.json` 生成，不手写」。这份清单登记
`src/api/**` 里每个请求 / 响应类型到底取自生成物还是手写，以及手写的原因——改类型前先在这里查一眼，
改完顺手同步这里。

## 一、生成物与命令

| 项                 | 位置 / 命令                                                                                         |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| 后端契约副本       | `src/api/generated/openapi.json`（**291 条路径 / 264 个 schema**，OpenAPI 3.1.0）                   |
| 生成的类型声明     | `src/api/generated/schema.d.ts`（`pnpm contract:write` 生成，**不手改**）                           |
| 拿类型的方式       | `import type { components } from '@/api/generated/schema'` → `components['schemas']['XxxResponse']` |
| 前后端契约漂移检查 | `pnpm contract:check`                                                                               |
| 与后端最新契约同步 | 根仓 `node scripts/frontend/sync-spec.mjs --repo user_client`                                       |

**覆盖范围（2026-10-23 刷新后）**：契约已从 identity 域的 51 条扩到 **291 条路径 / 264 个 schema**，
覆盖 auth / realname / api_key / resources / requirements / contracts / community / points / adapay / support 等；
本仓 `src/api/**` 目前只有 `realname`（14 个）与 `auth`（2 个）两类类型真的换成了生成物别名，
其余域仍手写——**下一步就是按域把它们逐个改成别名**，不用等后端了。

## 四、其余域：等后端产出后再迁

| 目录 / 文件                                                                                                                                        | 状态                 |
| -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| `src/api/points/`、`coupons.ts`、`community/`、`tickets.ts`、`contracts/`                                                                          | 后端未产出契约，手写 |

| `src/api/requirements/`、`devRequirements.ts`、`devOrderDeposit.ts`、`devWallet.ts`、`devCredit.ts`、`devDashboard.ts`、`requirementAgent.ts`      | 同上                 |

| `src/api/team.ts`、`invite.ts`、`tips.ts`、`settings/`、`publicProfile.ts`、`conversations.ts`、`oauth.ts`、`oauthAuthorizations.ts`、`support.ts` | 同上                 |

契约里 `api/user` 那两条是「OAuth / 实名系统端点」（`/user/oauth/{provider}/system`、
`/user/realname/system`），与本仓 `src/api/oauth.ts` 等模块对不上，别硬套。

迁一个域的动作是固定的：后端把该域写进 `openapi.json` → 根仓 `sync-spec.mjs` 同步副本并重新生成
`schema.d.ts` → 把该域 `types.ts` 里的手写类型换成生成物别名 → `pnpm type-check` / `pnpm test:ci` 全绿后
更新本文。**不要为了「看起来一致」手写一份像契约的类型**。

## 五、改这类类型时的三条口径

1. **形状一致才换别名**：字段名、可选性、可空性都对得上，才把 `type X = components['schemas']['Y']`。
2. **手写更严就保留收窄**：用 `Omit` / 交叉在别名上表达，并在注释里写清「比契约更严，因为 X」，
   不要为了贴合契约把必填改回可选。
3. **调用点优先**：类型换成生成物后如果调用点报错，**在 api 层调整别名**（收窄或放宽），不改页面。
   放宽的地方必须留下注释说明为什么，避免下次有人当成疏漏又改回去。

硬约束：`schema.d.ts` 不手写修改；出现报错不许用 `any` / `@ts-ignore` / `as unknown as` 抹平。
