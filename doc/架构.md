## 一、形态

单个 SPA，一套路由树同时装下需求方与开发者两种视角。开发者工作台不是独立工程，而是同一应用内的另一个区域——由路由 `meta.devArea` 标记，侧边栏据此切换菜单。这个设计带来一条容易踩的约束：**新增开发者页面必须带 `devArea`**，否则进页时侧边栏会当它是用户页面、切回用户工作台（`router/dev.ts` 里为团队、消息中心等路由专门写了注释说明）。

## 三、路由

`src/router/index.ts` 是唯一装配点，两条来源合并：

1. `devRoutes`（来自 `router/dev.ts`）：`/dev/**` 的**历史路径**，全部是重定向——例如 `/dev/resources` → `dev-plugins`，`/dev/requirements/my` → `dev-my-requirements`。它们只为保住旧链接能打开。
2. `devWorkbenchRoutes`（同样来自 `router/dev.ts`）：`developer/*` 相对路径，作为**工作台路由的子数组**挂载（`index.ts` 中 `...devWorkbenchRoutes`）。

主路由的一级路径覆盖首页、资源大厅、社区（含帖子详情）、搜索、支付、邀请与榜单、徽章、用户主页、团队、个人中心、工作台、消息中心、工单、实名、优惠券领取、积分商城、条款/隐私、退款、合同签署、资源详情，以及 `/:rootSlug/:entrySlug?` 这类动态首屏路径。

历史模式由 `VITE_ROUTER_MODE === 'history'` 决定，默认 hash（与 `admin_client` 同一约定）。`index.ts` 里还有一条 `SPA_FALLBACK_REDIRECT_PARAM = '__spa_redirect'` 的兜底参数，用于从静态 404 页把用户送回 SPA 内部路径。

## 四、守卫与登录态

`installDevRouteGuard(router)`（`router/dev.ts`）是开发者相关路径的守门人，判定顺序：

1. 既不是 `/dev/**` 也不是 `meta.devArea` 的路由，直接放行。
2. `auth.hydrate()` 恢复登录态。
3. **OAuth 回跳令牌兜底**：hash 模式下来自跨站的 `?oauth_token=` 位于 `#` 之前，不会出现在 `to.query` 里，所以额外从 `window.location.search` 取一次，取到后写进 store、清掉地址栏参数。
4. 未登录时统一走 `buildUnifiedAuthUrl('login', ...)` 跳到登录入口（不是简单的本地 `/login`）。
5. `meta.requiresRealname`：查 `getMyRealnameVerification`，非 `approved` 或 404 都跳实名页并带 `redirect_to`；接口异常则放弃导航（保留登录态、不误登出）。
6. `meta.requiresDevAccess`：`auth.ensureDevAccess()` 为假时跳 `dev-no-access`。

> 注意 `dev-home` 刻意**不带** `requiresRealname`：落地页若要求实名，未实名开发者一进来就被弹走，看不到任何概览数据。这是有意为之，不是漏写。

`src/router/index.ts` 另有全局守卫处理微信支付回跳等场景（`utils/wechatPayment` 的 `isWechatPaymentHandoff`）。401 的失效令牌由 `api/authEvents.ts` 广播，`App.vue` 监听后自动登出并弹登录框。

## 五、API 层与后端路径重写

前端调用里写的是「前端路径」，真正发出去前由 `src/shared/api/url.ts` 的 `normalizeBackendPath()` 改写成后端真实路径。**文档与排查 404 时一律以后端真实路径为准。**

| 前端路径 | 后端路径 |
| --- | --- |
| `/requirements` | `/requirement` |
| `/public/requirements` | `/requirements` |
| `/dev/requirements` | `/requirement` |
| `/dev/requirements/mine` | `/requirement/dev/mine` |
| `/payments`、`/dev/payments` | `/payment` |
| `/contracts`、`/dev/contracts` | `/contract` |
| `/coupons` | `/coupon` |
| `/dev/resources` | `/resources` |
| `/dev/credit` | `/credit/credit` |
| `/team/teams` | `/teams` |
| `/team/invitations` | `/teams/invitations` |
| `/settings` | `/system/settings` |
| `/resources/tags` | `/tag/tags` |

`normalizeBackendPath()` 的完整行为：先补前导 `/`；命中 `/uploads` 前缀的直接返回（静态资源不重写）；否则剥掉已有的 `/api` 前缀、查别名表替换、再补回 `/api`。`apiUrl()` 对已经是 `http(s)://` 的地址原样返回。`apiBaseForPath()` 有个特例：`/uploads` 且 `VITE_API_BASE_URL` 以 `/api` 结尾时，要把 `/api` 去掉再拼。

## 六、构建期特例

- `tags-wasm` 通过 `vite-plugin-wasm` 加载，依赖 `tags-wasm/pkg` 已构建（`link:../tags-wasm/pkg`）。
- `unplugin-auto-import` 与 `unplugin-vue-components` 生成 `auto-imports.d.ts`、`components.d.ts`，**这两个文件是入库的**，改动后会产生 diff。
- Element Plus 通过 `unplugin-vue-components` 的 `ElementPlusResolver` 按需引入，且 `importStyle: false`（样式另行处理）。
- `vite.config.ts` 在构建期把 `public/.htaccess` 复制到 `dist/.htaccess`。

## 七、富文本与前端净化

富文本编辑器用 tiptap（`@tiptap/*`，含表格、链接、代码块扩展），渲染走 `markdown-it`，净化走 `src/utils/sanitizeHtml.ts` 的 DOMPurify 封装。**前端净化只是第一道**，后端还会用 ammonia 再净化一次，且 URL 有白名单校验——两端都必须过，不要因为前端已净化就省掉后端。
